# 约场：场地评价与用户动态功能调研

> 调研日期：2026-09-12
>
> 目的：记录场地评价与用户动态的一手调研、Grill 决策和第四阶段边界。
>
> 边界：本文记录产品与技术调研及已锁定方案，不构成法律意见；最终实施顺序和契约以 `实施计划.md` 为准。

## 1. 结论摘要

“场地评价”“找搭子/约球”“用户动态”“评论互动”不是同一个功能包，应分别判断：

| 能力 | 主要问题 | 最自然的业务对象 | 对预约的作用 | 当前相对成本 |
|---|---|---|---|---|
| 场地评价 | 帮用户判断场馆是否值得预约，并给场馆提供履约反馈 | 已完成预约、场馆 | 交易后建立信任，可能影响下一次转化 | 中 |
| 找搭子/约球 | 解决“有场没人”或“有人没场”的组局问题 | 运动、时间、场馆/具体场次、人数、水平 | 交易前促成组局和预约 | 中高 |
| 用户动态 | 让用户表达、展示和持续回访 | 用户发布的图文/视频 | 与预约可以弱关联，也可能完全无关 | 高 |
| 评论互动 | 围绕评价、约球局或动态继续讨论 | 被评论内容、回复链 | 放大互动，也同步放大治理负担 | 高，且取决于挂载对象 |

一手资料验证了两类常见路径：本地生活平台以真实体验评价帮助消费决策，并允许商户回应；羽毛球产品则更常把社交绑定到订场、组局、活动或球技匹配。大众点评官方应用说明强调用户实地打卡照片和评价用于选择商户，其商户认证页明确提供“用户口碑，随看随回”；六个羽友官网将找球场、组队约球和找搭子放在同一产品定位中；羽约运动官方应用说明把好友打球动态、订场同步和按习惯/时段/球技组局串在一起。[大众点评 App Store 页面](https://apps.apple.com/cn/app/%E5%A4%A7%E4%BC%97%E7%82%B9%E8%AF%84-%E5%90%83%E5%96%9D%E7%8E%A9%E4%B9%90%E6%8C%87%E5%8D%97/id351091731)、[大众点评商户认证](https://www.dianping.com/business/vshop/)、[六个羽友官网](https://www.liugeyuyou.com/)、[羽约运动 App Store 页面](https://apps.apple.com/cn/app/%E7%BE%BD%E7%BA%A6%E8%BF%90%E5%8A%A8/id1450914782)

自由动态并非“评价多加一个发布页”。一旦允许公开动态、评论、回复或点赞，产品需要同时承担身份认证、内容审核、实时巡查、举报、申诉、违规处置、记录保存和用户分级等责任。《互联网跟帖评论服务管理规定》明确把评论、回复、留言、弹幕和点赞纳入跟帖评论服务范围；《网络信息内容生态治理规定》要求平台建立用户注册、账号管理、信息发布审核、跟帖评论审核、实时巡查和应急处置等制度。[《互联网跟帖评论服务管理规定》](https://www.cac.gov.cn/2022-11/16/c_1670253725725039.htm)、[《网络信息内容生态治理规定》](https://www.cac.gov.cn/2019-12/20/c_1578375159509309.htm)

因此，本轮 Grill 首先要决定的不是“动态页面长什么样”，而是平台要解决哪一个核心问题，以及是否愿意承担持续内容运营责任。

## 2. 当前项目事实

### 2.1 已确认范围

- `PRD.md` 和 `docs/功能完善调研报告.md` 已将评价、动态与找搭子纳入独立第四阶段；当前源码尚未实现这些能力。
- 当前源码仍是“找场馆 / 我的预约 / 我的”三 Tab；总功能报告的前三阶段目标为四 Tab，第四阶段完成后调整为“订场 / 动态 / 预约 / 会员 / 我的”五 Tab。
- 当前预约已经保存用户、场馆、场地、运动、时间和价格快照，并具有 `COMPLETED` 终态；这些事实能支持“谁在哪个场馆完成过哪次体验”的评价资格判断。
- 当前用户身份由小程序会话解析，`AuthContext.getMiniUserId()` 是现有 Controller 获取当前用户的统一入口。
- 当前场馆详情由 `MiniVenueController.getVenue()` -> `VenueServiceImpl.getPublicVenue()` -> `PublicVenueDetailVO` 返回，是展示评价摘要和评价列表入口的自然位置。
- 当前 `BookingServiceImpl.getUserBooking()` 已校验预约属于当前用户；评价资格可以复用同一归属事实，但不应把评价状态塞进预约状态机。

### 2.2 图谱核对结果

代码知识图谱已索引当前仓库（2609 个节点、7882 条边）。针对 `review / rating / comment / post / feed / social` 及中文“评价 / 评论 / 动态 / 找搭子 / 约球”的源码搜索没有发现现成业务实现；英文 `report` 命中的是经营报表，不是内容举报。

当前只有场馆封面和场地图片上传：场馆后台通过 `VenueServiceImpl.saveImage()` 保存到本地上传目录，并由 `/uploads/**` 暴露。它不是用户媒体系统，缺少用户上传权限、内容检测、异步审核状态、删除联动和生产对象存储，因此不能直接把现有上传接口当作动态图片能力。

### 2.3 最自然的扩展位置

| 新能力 | 可复用的现有事实 | 建议边界 |
|---|---|---|
| 评价资格 | `s_booking.user_id / venue_id / status`，当前用户归属校验 | 独立评价 Service 和表；预约只提供资格与快照，不新增“已评价”生命周期状态 |
| 场馆评分展示 | `MiniVenueController.getVenue()`、`PublicVenueDetailVO` | 详情返回评分摘要；是否在场馆列表返回摘要由性能和排序需求另行确认 |
| 用户身份 | `AuthContext.getMiniUserId()`、现有用户资料 | 复用平台用户，不创建第二套社区账号 |
| 找搭子 | 场馆、运动、具体场次和预约快照 | 使用独立招募状态，不复用 `BookingStatus`；开启招募必须绑定本人一笔 `CONFIRMED` 预约 |
| 场馆回复 | 场馆后台会话与场馆归属 | 回复只能代表当前场馆；与用户评论回复分开授权 |
| 内容通知 | 现有 `s_notification` 目前围绕预约 Mock 通知 | 可以借鉴发送记录模式，但评论提醒是否进入同表需在通知领域扩展时核对，不先假定 |
| 用户图片 | 现有本地场馆图片保存 | 只可借鉴最基础文件落盘方式；生产 UGC 媒体需独立审核、归属和删除流程 |

### 2.4 已锁定的前置边界

- 前三阶段先完成顾客/会员、储值、线上支付、权限和报表；平台会员视图只返回场馆级汇总，不查看个人会员资料或逐笔流水。
- 核心业务数据、状态机、审计、幂等和异常恢复按可上线标准实现。微信登录、支付/退款、订阅消息、媒体存储和内容检测使用可替换的 Mock 或本地 Adapter，模拟只替代外部渠道。
- Redis 业务锁使用 `sports-booking:lock:` 根前缀和 30 秒租期，覆盖完整数据库事务；P4 的找搭子并发与数据库约束共同保护。
- 线上预约以 `PAYING / PAID / REFUNDING / REFUNDED / PAYMENT_FAILED / REFUND_FAILED` 表达整体收款结果；外部支付/退款记录另保留待处理、成功、失败和关闭状态，并支持幂等通知、主动查单、超时关闭与异常对账，不能因使用 Mock 固定为立即成功。
- 线下预约只登记并占用具体场次，不进入支付、退款、余额、核销或未到场流程，结束后进入 `ENDED_UNTRACKED`。

## 3. 一手产品观察

### 3.1 场地评价：服务于选择与经营

大众点评官方应用说明把用户实地打卡照片和评价定位为商户选择依据；官方商户认证页说明认证商户可以管理用户口碑并回应。美团现行评价规则进一步把用户商品/服务评价及用户或商户的回应都定义为点评信息，形式可包含文字、图片和视频。[大众点评 App Store 页面](https://apps.apple.com/cn/app/%E5%A4%A7%E4%BC%97%E7%82%B9%E8%AF%84-%E5%90%83%E5%96%9D%E7%8E%A9%E4%B9%90%E6%8C%87%E5%8D%97/id351091731)、[大众点评商户认证](https://www.dianping.com/business/vshop/)、[美团网平台点评规则](https://portal-portm.meituan.com/webpc/protocolmanage/comment/judge)

美团 2025 年发布的现行评价细则强调真实、客观和关联性：平台可核验消费凭证，并对虚假评价、利益诱导评价、利益相关方评价、与消费体验无关的内容采取不展示、折叠或不计分等处理。该规则不能直接照搬为约场规则，但说明“谁有资格评价、什么内容计入评分、异常评价如何处理”必须在上线前明确。[美团评价规则（细则）](https://rules-center.meituan.com/m/detail/guize/185?activeRule=1)

对约场的可验证启示：

- 场地评价的核心价值是预约决策和场馆改进，不等同于社区活跃。
- 已完成预约能提供强资格凭证；是否允许未在平台预约但线下到店的用户评价，是另一套真实性与举证规则。
- “评价展示”和“评分计入”可以是两个口径；被折叠或待复核内容是否计分需要明确。
- 场馆回复是经营沟通；开放用户互评或楼中楼会把评价功能扩成社区互动。

### 3.2 找搭子/约球：服务于组局完成

六个羽友官网将产品描述为“订场约球平台，帮球馆引流，帮球友找搭子”，并明确帮助球友找附近球场、组队约球；这是一条从供给发现到组局的结构化路径，而不是单纯内容流。[六个羽友官网](https://www.liugeyuyou.com/)

羽约运动官方应用说明提供三个更具体的绑定点：同步好友打球动态、把订场信息同步给受邀球友、根据打球习惯推荐时段和球友，并在运动后按球技数据匹配对手发起约球。[羽约运动 App Store 页面](https://apps.apple.com/cn/app/%E7%BE%BD%E7%BA%A6%E8%BF%90%E5%8A%A8/id1450914782)

对约场的可验证启示：

- 找搭子的信息最少需要运动、时间、地点、人数和参与状态；水平、费用和性别偏好是否需要，应由目标用户场景决定。
- 绑定现有具体场次可直接促成预约和避免地点/时间歧义，但会限制“先找人再订场”的场景。
- 不绑定具体场次则要处理地点变更、时间变更、取消、人数满员、候补和爽约等独立状态。
- 找搭子的核心指标应是成局、到场和预约转化，不是发帖量本身。

### 3.3 用户动态：服务于内容消费与关系沉淀

中羽联官方应用说明展示的是更宽的社区形态：与羽毛球爱好者交朋友、观看羽毛球视频、讨论装备和二手装备置换。这类内容可以脱离单次预约存在，内容供给、关系和持续分发本身就是产品。[中羽联 App Store 页面](https://apps.apple.com/cn/app/%E4%B8%AD%E7%BE%BD%E8%81%94/id1578165198)

对约场的可验证启示：

- 自由动态不是预约功能的自然附属；需要回答用户为什么在这里发，而不是发到微信群、小红书或现有球友社区。
- 图文、视频、装备交易、技术讨论和战绩分享是不同内容类型，不能因都叫“动态”就一次性纳入。
- 关注关系、推荐流、热榜和私信不是发布动态的必然前置条件；每增加一项都会新增冷启动、风控和隐私边界。
- 如果动态不能产生预约、组局或会员复购的可观测结果，它可能增加停留时长，却未必改善当前双边平台目标。

## 4. 冷启动与效果验证

以下为结合当前项目的设计推论，不是外部产品已证明的效果。

| 能力 | 首批内容从哪里来 | 冷启动难点 | 建议观察指标 |
|---|---|---|---|
| 场地评价 | 已完成预约用户的真实体验 | 早期评价少，单条极端评价容易扭曲印象 | 可评价预约数、发布率、有效评价覆盖率、详情到预约转化、场馆回复率 |
| 找搭子/约球 | 有明确时间计划的用户、场馆或俱乐部发起的球局 | 同城、同运动、同时间三重密度不足 | 发布到满员时长、成局率、到场率、由球局带来的预约数、取消/爽约率 |
| 用户动态 | 用户原创、场馆官方内容、活动回顾 | 空 feed、内容质量不稳定、创作者持续性不足 | 周发布用户、有效互动用户、内容到场馆详情/预约转化、举报率 |
| 评论互动 | 评价、球局或动态的浏览用户 | 没有母内容就没有评论；争执和广告比正文更快增长 | 有回复内容占比、有效对话率、举报率、处置时长、评论到成局/预约转化 |

演示数据若包含生成的评价或动态，应由独立 Demo 开关隔离并在数据说明中标明来源，业务界面不逐条显示演示标记；正式环境默认关闭 Demo 数据和真实用户公开发布入口。真实试点时应把“内容量”与“业务结果”分开看，避免用浏览量替代预约转化或成局率。

## 5. 功能组合选项

以下是 Grill 过程中评估过的组合。最终已选择“评价 + 找搭子 + 自由动态社区”的收紧版本，锁定规则见第 11 节；未被第 11 节纳入的能力不实施。

### 选项 A：只做已履约场地评价

最小能力：完成预约后评分、结构化标签和文字评价；场馆单次官方回复；场馆详情展示评分摘要和评价列表；用户/场馆举报；平台审核与申诉。

可暂不加入：用户互评、楼中楼、点赞、关注、动态流、图片/视频。图片不是评价成立的必要条件，暂缓可以避开异步媒体审核和存储扩容。

适合验证：评价是否提升场馆详情到预约转化，以及场馆是否会使用反馈改进经营。

### 选项 B：评价 + 结构化找搭子/约球

在 A 之外增加约球局：运动、日期时间、场馆/具体场次、目标人数、参与申请、满员、取消和结束。是否支持先组局后订场、费用 AA、候补和爽约记录仍需 Grill。

可暂不加入：自由图文动态、关注、推荐算法、私信。球局详情可以有一层留言，但这会立即触发评论治理要求，需单独确认。

适合验证：平台是否能把单人订场需求变成多人到场，并形成新增预约。

### 选项 C：评价 + 找搭子 + 自由动态社区

增加用户图文/视频动态、评论回复、点赞、关注、用户主页和内容流。该选项的核心产品从预约平台扩展为内容社区，需要持续内容供给、内容运营、审核人员和用户治理。

仍不应默认加入：私信、群聊、二手交易、算法推荐、热榜。它们分别引入通讯安全、交易风控、算法治理或更强的舆情风险，应按独立需求决定。

### 选项 D：评价 + 找搭子，不开放自由动态

这是 B 的另一种长期边界：平台保留交易评价和结构化球局，用户内容只围绕真实履约或明确组局对象产生。它牺牲通用内容表达，但可以把内容密度和业务指标集中在预约与到场。

## 6. 数据模型影响

以下是已确认的模型边界，随 P4 迁移实现。不得先建通用 `s_content` 引擎；评价、找搭子和动态的状态、归属与删除规则不同，审核、举报、申诉和处置日志才共享治理模型。

### 6.1 场地评价模型

| 模型 | 最小职责与约束 |
|---|---|
| `s_venue_review` | 关联 `booking_id / venue_id / user_id`，`booking_id` 唯一；保存当前版本、公开版本、内容状态和时间 |
| `s_venue_review_revision` | 保存评价每次创建或修改的不可变正文版本，并区分待审版本和已公开版本 |
| `s_venue_review_reply` | 场馆单条官方回复，`review_id` 唯一；保存场馆、操作者和状态，修改另存不可变回复版本 |
| `s_venue_review_media` | 保存最多 3 张图片的归属、地址、顺序和审核状态；评价不支持视频 |
| `s_content_report` | 举报目标、举报人、原因、状态、处理人与处理结果；目标类型只允许已确认的公开内容 |
| `s_content_moderation_log` | 记录机器结果、人工决定、隐藏/恢复/删除和申诉结果，不覆盖原始内容事实 |

评价包含总体、场地、环境、服务四项评分；只有正常公开评价的总体评分计入场馆总分。用户可匿名展示，完成后 30 天内发布、发布后 7 天内修改、删除后不能再次评价。

### 6.2 找搭子模型

| 模型 | 最小职责与约束 |
|---|---|
| `s_post_recruitment` | 绑定动态与本人一笔已确认预约，保存运动水平、需要人数、免费/预计 AA 金额、说明和招募状态 |
| `s_post_recruitment_member` | 参与人申请、通过、拒绝、退出和移除状态；同一用户同一招募唯一 |

招募状态为招募中、已满员、已关闭、预约已取消和已结束。申请由发起人处理，不做候补；预约取消、动态删除或双方拉黑时按规则关闭招募或退出参与关系。

### 6.3 动态模型

| 模型 | 最小职责与约束 |
|---|---|
| `s_post` | 保存用户、场馆或平台作者、当前版本、公开版本、官方/置顶、评论开关和内容状态 |
| `s_post_revision` | 保存动态每次创建或修改的不可变正文版本，并区分待审版本和已公开版本 |
| `s_post_media` | 图片/视频地址、顺序、审核状态和异步检测任务标识 |
| `s_post_comment` / `s_post_comment_revision` | 纯文字/表情一级评论与单层回复；修改正文保存不可变版本 |
| `s_post_like` | 同一用户对同一动态最多一个有效点赞 |

动态还要求用户侧“我的发布/删除/申诉”和平台侧“待审/举报/处置/账号限制”界面，不是只增加一组小程序页面。关注、推荐算法、热榜、私信和群聊均不建模。

## 7. 接口与页面影响

### 7.1 若选择场地评价

- 用户端：查询评价资格、创建/编辑或删除评价、查看本人评价、举报评价/回复。
- 场馆详情：评分摘要、标签分布、评价列表、场馆官方回复。
- 场馆后台：评价列表、回复、举报或申诉入口；不能直接修改用户评价。
- 平台后台：待复核内容、举报、申诉、处置记录和用户限制。
- 预约详情：只返回评价资格和评价 ID，不改变预约状态。

### 7.2 若选择找搭子/约球

- 用户端：动态可选绑定本人一笔已确认预约；绑定后可开启找搭子，并完成详情、申请、审批、退出、移除和关闭。
- 公开页展示场馆、运动、日期时间和招募人数；场地编号只对已通过成员展示，预约码、付款信息和联系方式不公开。
- 场馆后台不代用户创建找搭子或管理申请；场馆官方内容由具有对应角色权限的员工发布。
- 通知：申请、通过、满员、取消和临近开始；当前 Mock 通知可表达演示状态，但真实微信消息授权仍是后续能力。

### 7.3 若选择自由动态

- 小程序需要动态流、发布器、详情评论、用户主页、我的发布和举报/申诉。
- 后端需要分页流、内容归属、可见性、审核状态、媒体异步回调、计数一致性和删除传播。
- 管理后台需要内容审核、举报队列、申诉、账号限制与处置审计。
- 已确认第四阶段建立一级“动态”Tab，并将最终导航调整为五 Tab；这属于计划，当前源码尚未实现。

## 8. UGC 治理与合规最低边界

### 8.1 法规明确要求

《互联网跟帖评论服务管理规定》适用于具有舆论属性或社会动员能力的平台提供的评论、回复、留言、弹幕、点赞等服务。规定要求服务提供者按“后台实名、前台自愿”进行真实身份认证，建立个人信息保护、审核管理、实时巡查、应急处置和举报受理制度，配备与规模相适应的审核队伍；还要求与用户签订服务协议、对违规内容和账号采取处置并保存记录、建立用户分级/黑名单，以及提供投诉举报和申诉入口。[《互联网跟帖评论服务管理规定》第 2、4、6、7、8、13 条](https://www.cac.gov.cn/2022-11/16/c_1670253725725039.htm)

《互联网用户账号信息管理规定》要求提供信息发布、即时通讯等服务时进行真实身份认证，并要求平台建立真实身份认证、账号核验、信息内容安全、生态治理、应急处置和个人信息保护制度。[《互联网用户账号信息管理规定》第 9、14 条](https://www.cac.gov.cn/2022-06/26/c_1657868775042841.htm)

《网络暴力信息治理规定》自 2024 年 8 月 1 日施行，要求信息发布服务建立发布审核、监测预警、识别处置等制度；对异常账号和浏览、评论、举报量显著增长等风险采取核验、提示、警示或限制流量等措施，并对违法信息停止传输、保存记录和依法报告。[《网络暴力信息治理规定》第 7、8、12 至 15 条](https://www.cac.gov.cn/2024-06/14/c_1720043894161555.htm)

精确位置属于敏感个人信息。若找附近球友或动态位置使用精确定位，《个人信息保护法》要求具有特定目的和充分必要性、采取严格保护措施并取得单独同意；不满十四周岁未成年人的个人信息也属于敏感个人信息。[《中华人民共和国个人信息保护法》第 28、29、31 条](https://www.npc.gov.cn/WZWSREL25wYy9jMi9jMzA4MzQvMjAyMTA4L3QyMDIxMDgyMF8zMTMwODguaHRtbD9yZWY9aW1i)

是否达到“具有舆论属性或社会动员能力”、是否需要新功能安全评估以及正式实名方案，应在真实上线前由合规人员结合运营规模和形态判断。当前 Mock 登录不能作为已满足真实身份认证的证据，也不能仅凭微信 `openid` 推断已经满足全部实名要求。

### 8.2 微信官方能力的边界

微信官方 `msgSecCheck` 必须在服务端调用，可检测资料、评论、论坛和社交日志场景的文本，并返回 `pass / review / risky` 建议；它是检测工具，不是平台治理制度。[微信开放文档：文本内容安全识别](https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/api_msgseccheck.html)

微信官方 `mediaCheckAsync` 用于异步检测图片/音频；结果通过消息服务器回调，官方文档说明异步结果会在 30 分钟内推送。因此用户媒体不能按“上传即公开”设计，至少需要待检测状态、回调匹配、超时/失败处理和人工复核路径。[微信开放文档：多媒体内容安全识别](https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/api_mediacheckasync.html)

最低闭环应包含：

1. 发布前文本检测；`review` 进入人工队列，`risky` 拒绝或隐藏，不能把机器结果当最终申诉结论。
2. 图片/音频先保持非公开，收到异步检测通过后再公开；检测超时或失败不能默认放行。
3. 用户可举报公开内容和账号，并查看处理状态；被处置用户有申诉入口。
4. 平台人员可隐藏、恢复、删除内容，限制用户发布/评论，并保存操作者、原因和时间。
5. 用户协议、社区规则和隐私说明明确发布权限、禁止内容、数据用途、保存期限和处置规则。
6. 场馆只能管理自己的官方回复或提交举报，不能直接删除不利评价；平台处置与场馆经营权限分开。

这些能力不能因项目是演示版就被写成已上线可用。已确认方案使用独立 Demo 开关隔离虚构内容，界面不逐条显示演示标记；正式环境必须默认关闭 Demo 数据与真实用户公开发布入口。

## 10. Grill 问题（已完成）

以下问题是本轮访谈的决策树和审计记录，最终结论见第 11 节。

### 产品目标

1. 首要目标是提升场馆预约转化、促成球局，还是增加用户内容消费与回访？只能选一个第一指标。
2. 这批能力只用于高完成度演示，还是计划进入真实用户试点？真实发布会直接触发持续治理与合规投入。
3. 社交能力是否只服务羽毛球主场景，还是从第一版就覆盖全部运动类型？

### 场地评价

4. 谁可以评价：仅 `COMPLETED` 的线上预约用户，还是线下预约、`NO_SHOW` 或无平台预约用户也可以？
5. 一笔预约只能评价一次，还是允许修改、追加评价？允许修改时是否保留版本与原评分？
6. 评分只用总分，还是环境、设施、服务、卫生等维度？哪些维度进入场馆总分？
7. 第一版是否允许图片？若允许，能否接受图片检测完成前不公开？
8. 场馆只能回复一次，还是可以与用户连续对话？连续对话会把评价升级为评论区。
9. 用户是否可匿名展示？无论前台是否匿名，后台身份与违规记录如何保留？
10. 评价被举报、申诉或隐藏时，是否继续计入总分？

### 找搭子/约球

11. 球局必须绑定一个已订具体场次，还是允许先组人再订场？
12. 谁能发起：所有实名用户、完成过预约的用户、会员、场馆或俱乐部？
13. 加入是直接成功还是发起人审核？满员后是否候补？
14. 第一版是否涉及 AA 费用、代收款或退款？若不涉及，页面是否明确“平台不代收球局费用”？
15. 水平、年龄、性别偏好哪些是必要筛选？如何避免歧视、不实资料和敏感个人信息过度收集？
16. 发起人取消、参与者退出或爽约如何记录；是否影响之后的发布/参与权限？
17. 球局是否需要留言？如果只是协调，能否用固定选项和发起人公告替代开放评论？

### 用户动态与互动

18. 用户可以发布什么：仅运动记录/战绩、场馆打卡、技术交流，还是任意体育内容？
19. 动态是否必须关联场馆、运动、预约或球局中的至少一个？
20. 第一版需要文字、图片还是视频？每增加一种媒体都对应不同的存储与审核链路。
21. 互动只做点赞，还是评论、回复、关注也做？四者不是一个开关。
22. 内容流按同城、运动、关注还是时间排序？是否真的需要算法推荐？
23. 是否允许展示精确距离或位置？用场馆位置/行政区能否满足，而不暴露用户实时位置？
24. 是否允许未成年人发布、被评论或参与陌生人球局？若允许，监护和隐私规则如何处理？

### 治理与运营

25. 谁负责日常审核、举报和申诉，响应时限是多少？没有责任人就不应开放真实 UGC。
26. 机器检测返回 `review`、超时或不可用时，是待审、拒绝发布还是限流展示？
27. 哪些场馆员工有回复权；平台和场馆分别能看到哪些用户信息？
28. 用户删除内容、账号注销、违规证据保存和备份删除之间如何取舍？
29. 演示数据由谁提供，如何统一标记，如何确保不使用真实手机号、头像、聊天和位置？
30. 哪组指标达到什么阈值后，才继续投入自由动态、关注或推荐流？

## 11. 已确认方案

### 11.1 产品目标与阶段

- 社交能力的第一指标不是停留时长，而是评价对预约转化的帮助、动态到场馆/预约的点击，以及找搭子申请与成局。
- 评价和动态作为独立第四阶段，依赖前三阶段完成预约、会员、收银、权限和报表闭环。
- 第四阶段仍是本地高完成度演示，不向真实公众开放；所有功能覆盖当前平台运动类型，不只服务羽毛球。
- 真实开放前必须另行完成真实身份认证、生产媒体存储、内容安全检测、未成年人方案和持续审核责任配置。

### 11.2 场地评价

- 仅本人名下 `COMPLETED` 预约具备评价资格，每笔预约最多一条；`NO_SHOW`、已取消和无平台预约用户不能评价。
- 预约完成后 30 天内可发布；发布后 7 天内可修改，修改重新进入当前审核规则；用户可随时删除，删除后同一预约不能重新评价。
- 每次修改保存不可变内容版本；审核开启时旧的已通过版本继续公开，新版本通过后再替换。
- 内容包含 1 至 5 星总体评分、场地/环境/服务分项、最多 3 个平台按运动维护的固定标签、正文和最多 3 张图片，不支持视频评价。
- 场馆总分使用正常公开评价的总体评分平均值；分项用于分析。待审、隐藏、拒绝和删除评价不计分，恢复后重新计入。
- 用户可选择匿名展示；公开页只显示“已到场”、运动类型和到场月份，不显示具体日期、时间或场地编号，后台保留真实用户与预约关联。
- 场馆可发布一条官方回复，允许修改但必须保留记录；评价区不开放其他用户评论、回复或点赞。

### 11.3 用户动态与公开身份

- 所有登录用户均可发布，但内容必须属于运动主题、选择一个平台运动类型并填写正文；场馆与预约关联可选。
- 每条动态最多 3 张图片，或 1 个不超过 20 秒且不超过 30 MB 的视频；图片与视频不能混发，单张图片不超过 5 MB。
- 动态、评论和找搭子参与者展示昵称与头像，不允许匿名；公开主页只展示昵称、头像、运动类型和公开动态。
- 信息流默认按发布时间倒序，支持运动类型和场馆筛选；不做关注关系、关注流、推荐算法、热榜、私信或群聊。
- 动态支持点赞、纯文字/表情评论和单层回复。作者可在普通动态随时关闭评论；约球招募结束前不能关闭评论，关闭后历史评论继续显示。
- 评论发布后 10 分钟内可修改并重新进入当前审核规则；作者可删除自己的评论，有回复时保留“评论已删除”占位。动态作者不能删除他人评论，只能举报或拉黑。
- 动态发布后 30 分钟内可修改并重新进入当前审核规则，作者可随时删除；动态和评论修改均保存不可变版本，审核开启时旧的已通过版本继续公开，新版本通过后再替换。删除采用逻辑状态，不反向取消绑定预约。

### 11.4 预约绑定与找搭子

- 每条动态最多选择绑定本人一笔 `CONFIRMED` 预约；不绑定预约也允许发布。
- 公开页展示场馆、运动、日期时间和招募人数；场地编号仅对已通过成员展示，预约码、付款信息和联系方式永不公开。
- 绑定预约后作者可开启找搭子，填写运动水平、需要人数、预计“免费/AA 金额”和补充说明；平台不代收球局费用。
- 其他登录用户提交申请，由发起人同意或拒绝；不做候补。公开页只显示参与人数和少量头像，完整成员列表只对发起人和已通过成员可见。
- 参与者可退出，发起人可填写原因移除成员，不记录信用处罚或自动扣款。
- 状态为招募中、已满员、已关闭、预约已取消和已结束。预约取消时自动关闭招募并通知成员；到预约开始时间结束招募，历史内容保留。
- 删除动态时关闭招募并通知成员，但不取消预约；双方拉黑时自动退出或移除参与关系。参与者若没有本人名下的 `COMPLETED` 预约，不获得场地评价资格。
- 不允许在动态或评论公开手机号、微信号或个人二维码；协调通过公开评论、申请状态和系统通知完成。

### 11.5 审核、举报与账号治理

- 平台提供动态、评论、评价三个独立的全平台审核开关，评论开关同时覆盖单层回复，评价开关覆盖场馆官方回复。
- 开关开启后新内容进入待审，关闭后新内容立即公开；切换不改变历史公开或待审内容。默认三个开关全部开启。
- 场馆官方动态跟随动态审核开关；平台官方动态由平台管理员发布后直接公开。场馆员工发布官方动态或回复评价需要对应角色权限。
- 现有平台管理员负责通过、拒绝、隐藏、恢复和删除，不能修改用户原文；全部操作记录原因、人员和时间。
- 用户可按固定原因举报内容或账号并补充说明，同一用户对同一目标只保留一条处理中举报；每次处置允许被处置用户申诉一次。
- 平台可分别暂停用户发动态、评论和申请约球，支持 1/7/30 天或永久；预约、支付、已有预约查看和核销凭证默认不受内容处罚影响。
- 支持用户拉黑。双方动态与评论互相不可见，不能继续申请对方球局，已有参与关系自动退出或移除。
- 每用户每天最多发布 5 条动态、每小时最多 30 条评论/回复、每小时最多点赞 120 次；本轮不建设通用风控配置中心。
- 用户注销前必须结清余额，且不存在待支付或已确认未结束预约。注销后全部会话立即失效、拒绝同一身份重新登录、解除员工绑定，并从公共页面移除主页、动态、评论和评价。
- 注销立即清除用户资料中的联系人姓名和手机号；预约联系人快照、资金流水和必要治理证据仅在受限后台按保留规则留存。

### 11.6 页面、通知、分享与演示数据

- 小程序主导航为“订场 / 动态 / 预约 / 会员 / 我的”；“我的”中增加消息中心、我的发布、举报/申诉状态和公开主页入口。
- 评论、回复、场馆回复、约球申请/处理/取消、举报和申诉结果进入消息中心；点赞只展示聚合数量，不逐次通知。
- 支持分享动态、场馆评价列表和约球动态；内容隐藏、删除、取消或失效后，分享落地页显示明确状态。
- 平台最多置顶一条认证官方公告；用户和场馆动态不能手工或付费置顶。场馆官方账号可发布认证动态，普通员工需角色授权。
- Demo 开关为三家场馆生成评价、用户动态、官方动态和约球记录，界面不逐条显示演示标记；正式环境默认关闭，数据不得复用真实头像、手机号、聊天或位置。
- 第四阶段指标包括评价发布率、场馆详情到预约转化、动态到场馆/预约点击、约球申请与成局率、举报率和处理时长；不以发帖数和停留时长作为唯一成功指标。

### 11.7 明确非范围

- 关注、私信、群聊、推荐算法、热榜、内容付费置顶、二手交易和通用活动系统。
- 评论图片/视频/语音、视频评价、评价楼中楼和用户对评价点赞。
- 多预约绑定、候补、信用分、爽约处罚、平台代收 AA 费用和参与者自动获得评价资格。
- 用户实时位置、精确距离、公开联系方式、年龄/性别/职业筛选和未成年人身份采集。
- 真实微信内容安全、生产对象存储、视频转码和公开 UGC 运营。
