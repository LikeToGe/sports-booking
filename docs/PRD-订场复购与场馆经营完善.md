# 约场 PRD：订场复购与场馆经营完善

> 日期：2026-10-09。
> 来源：用户同意本轮竞品分析，并要求使用 to-prd 生成需求文档。
> 状态（2026-10-13）：P5/P6 功能已实现，构建与隔离业务验收通过；P6 完整端侧、无障碍与真机门禁仍待补验。实现与本次边界修复证据见 `docs/evidence/p5/README.md`、`docs/evidence/p6/README.md` 和 `docs/evidence/audit-fixes/README.md`。
> 基线：现有 P0-P4 工作区与领域词汇；本文件定义后续 P5/P6 增量，不把历史实现重新列为待开发。

## Problem Statement

用户通常先知道自己什么时候有空，再选择去哪家场馆。目前用户需要进入不同场馆逐一查看具体场次，首页的全天起价也不足以回答目标时段的实际价格。常去同一家馆的用户需要重复搜索、选日期和找场次；满场时无法留下需求，取消释放后也无法及时获知。

用户已有找搭子能力，但招募藏在普通动态中，缺少按日期、水平和剩余名额的专门检索。用户难以迅速判断哪些招募适合自己、仍可申请、且确实关联有效预约。

场馆已有总体利用率、取消率、复购率和经营日报，但仍需人工推断哪些星期、时段和场地需要经营。顾客档案与会员资金已有，近期未再预约的顾客缺少明确筛选和回访处理记录。预约确认、取消与赠送余额提醒已有消息能力，到场提醒和空位需求回流仍需形成可验证的闭环。

## Solution

沿用微信小程序和管理后台，将现有能力连成找场、再订、参加找搭子、空位提醒和场馆经营的完整路径。继续以郑州多场馆、羽毛球主场景为重点，底层支持现有平台运动类型。

| 阶段 | 交付范围 | 用户或场馆得到的结果 |
| --- | --- | --- |
| P5：订场与参与效率 | 按时段找空场；常约馆、收藏、再次预约；场次比较；找搭子检索 | 用户更快找到合适的一个具体场次或可申请的找搭子 |
| P6：需求回流与经营行动 | 开售/空位提醒；分时段经营分析；顾客分组与回访待办；到场提醒与预约服务 | 用户获得重新预约的机会，场馆能根据数据处理空闲与回访 |

P5 在现有预约、余额和找搭子规则上改善检索与入口；P6 复用现有报表和站内消息，补齐订阅、回访和提醒事实。提醒只提供信息，不保留具体场次，不自动创建预约或扣款。

连续场次、找搭子候补、场馆组织付费活动、次卡和课程保留为后续候选，不在 P5/P6 内。实施现有找搭子检索时遵循原 UGC 开关和审核边界，不因增加入口而开放真实公众 UGC。

## User Stories

1. 作为用户，我希望选择平台运动类型、预约日期和自己可用的时间范围，以便直接找到符合安排的具体场次。
2. 作为用户，我希望只看到能够完整落在所选时间范围内的具体场次，以便避免预约延伸到自己没空的时间。
3. 作为用户，我希望看到匹配时段的实际价格，以便比较场馆时不被全天最低价误导。
4. 作为用户，我希望按场馆名称、区县和单个具体场次价格筛选，以便缩小可接受的选择。
5. 作为用户，我希望在检索结果中直接看到场馆、场地、运动、开始结束时间和可订状态，以便无需反复进入场馆查找。
6. 作为用户，我希望进入场馆详情后保留之前的日期和时段条件，以便继续比较而不用重新填写。
7. 作为用户，我希望没有匹配结果时能明确看到原因并主动放宽条件，以便重新寻找而不被悄悄改变需求。
8. 作为用户，我希望创建预约前再次检查价格、具体场次和预约规则，以便列表过期时不会产生错误预约。
9. 作为用户，我希望收藏常用场馆并能取消收藏，以便管理自己的常约入口。
10. 作为用户，我希望收藏在同一账号的不同设备上保持一致，以便更换设备后仍能使用。
11. 作为用户，我希望看到自己最近预约过的场馆，以便快速返回常用场馆。
12. 作为用户，我希望从本人历史预约进入再次预约并选择新日期，以便复用场馆、运动和时段偏好。
13. 作为用户，我希望再次预约明确展示当前价格，以便知道历史价格不会自动沿用。
14. 作为用户，我希望偏好的具体场次不可用时看到明确提示和可选择的其他时段，以便自己决定替代方案。
15. 作为用户，我希望已停用场馆或场地在常约入口中明确显示不可订，以便避免误操作。
16. 作为用户，我希望收藏和历史预约只属于本人，以便其他用户无法读取我的偏好。
17. 作为用户，我希望按时间和场地比较具体场次，以便在同一时段选择合适场地。
18. 作为用户，我希望可订、支付占位、已预约和不开放状态有文字和视觉区分，以便理解不可订原因。
19. 作为用户，我希望比较页面不展示他人联系人、预约号或核销信息，以便场次状态不泄露隐私。
20. 作为用户，我希望选场时就能看到当前价格、取消截止和入场规则，以便在付款前理解条件。
21. 作为用户，我希望选场视图在手机上可读并能操作，以便较多场地时也能正常比较。
22. 作为用户，我希望只能选择一个可订具体场次，以便操作结果符合当前固定场次预约规则。
23. 作为用户，我希望在现有动态页切换到找搭子视图，以便集中查看正在招募的内容。
24. 作为用户，我希望按日期、平台运动类型、场馆、水平和剩余名额筛选找搭子，以便找到适合自己的招募。
25. 作为用户，我希望招募卡片显示时间、场馆、水平、人数、费用说明和预约有效性，以便申请前作出判断。
26. 作为用户，我希望费用明确区分免费与预计 AA，以便知道平台没有代收费用。
27. 作为用户，我希望从招募卡片进入现有详情申请加入并查看处理结果，以便完成现有申请流程。
28. 作为找搭子发起人，我希望沿用现有审核、退出、移除与关闭规则，以便新增入口不改变参与关系。
29. 作为用户，我希望已取消预约、过期、满员或不公开内容不被当成可申请招募，以便不会申请失效名额。
30. 作为用户，我希望分享链接打开失效招募时给出状态说明，以便不看到残留成员信息。
31. 作为用户，我希望 UGC 关闭时隐藏找搭子入口且接口拒绝访问，以便产品开关行为保持一致。
32. 作为用户，我希望报名相关行为继续遵守协议接受、内容限权和拉黑规则，以便新的列表不绕过治理。
33. 作为用户，我希望为指定场馆、运动、日期和时段登记开售或空位提醒，以便没有可订场次时留下需求。
34. 作为用户，我希望能查看并撤回提醒登记，以便安排变化后停止接收相关提醒。
35. 作为用户，我希望未开放日期进入可售窗口后收到开售消息，以便及时查询预约。
36. 作为用户，我希望取消或支付超时释放合适具体场次后收到空位消息，以便有机会再次预约。
37. 作为用户，我希望提醒明确说明具体场次未为我保留，以便不把消息误认为预约确认。
38. 作为用户，我希望同一空位事件不会重复提醒，以便避免重复消息干扰。
39. 作为用户，我希望打开提醒时重新检查库存并保留原筛选条件，以便具体场次已被订走时仍能寻找替代方案。
40. 作为用户，我希望过期、已撤回的登记不再收到提醒，以便系统遵守我的当前选择。
41. 作为场馆超级管理员，我希望按星期和时段查看可售与被预订时长，以便发现具体空闲窗口。
42. 作为有报表查看权限的场馆员工，我希望筛选日期、场地和运动并下钻具体场次，以便解释热力图结果。
43. 作为场馆超级管理员，我希望区分没有预约和根本不可售的时段，以便不将运营关闭误判为经营空闲。
44. 作为场馆超级管理员，我希望看到各场地利用率和取消情况，以便调整排期和经营重点。
45. 作为场馆超级管理员，我希望新分析保留线上经营、线下登记、余额消费和真实收款的独立口径，以便不误读资金。
46. 作为场馆员工，我希望统计显示口径、时间范围和数据生成时间，以便知道数字代表什么。
47. 作为平台管理员，我希望按现有权限查看场馆级经营分析，以便了解供给而不访问个人会员资料。
48. 作为有顾客查看权限的场馆员工，我希望按最近预约、已完成线上核销、预约次数和常约时段查看本场馆顾客，以便识别回访对象。
49. 作为有顾客经营编辑权限的场馆员工，我希望维护场馆内顾客标签，以便记录本场馆经营分类。
50. 作为有顾客经营编辑权限的场馆员工，我希望从近期未再预约分组创建回访待办，以便把分析转成具体工作。
51. 作为有顾客经营编辑权限的场馆员工，我希望记录待办完成、无需处理和备注，以便其他授权员工知道处理结果。
52. 作为有顾客查看权限的场馆员工，我希望分组不能读取其他场馆顾客，以便遵守场馆隔离。
53. 作为平台管理员，我希望只看到场馆级顾客经营汇总，以便沿用现有个人资料访问边界。
54. 作为场馆超级管理员，我希望权限撤销后下一请求立即禁止标签和回访编辑，以便保证授权及时生效。
55. 作为用户，我希望已确认预约在开始前收到一次到场提醒，以便及时安排出行。
56. 作为用户，我希望提醒消息直达本人预约详情，并能查看导航、入场须知和核销凭证，以便到场时无需重复找入口。
57. 作为用户，我希望预约取消、完成或失效后不再收到过期到场提醒，以便消息反映当前状态。
58. 作为用户，我希望临近开始才确认预约时也能得到一次有效提示，以便不会因错过固定调度点而遗漏。
59. 作为运营人员，我希望能区分站内消息已生成、Mock 投递成功与外部投递失败，以便排查消息而不虚报真实送达。
60. 作为运营人员，我希望调度重复运行或失败重试不会重复生成消息，也不改变预约和余额状态，以便提醒失败不影响主业务。
61. 作为用户，我希望加载失败时可重试、列表为空时有解释，以便区分没有供给和网络异常。
62. 作为用户，我希望所有状态同时有文字而非仅靠颜色，以便正常阅读和操作。
63. 作为项目验收人员，我希望可用同一组业务场景验证接口与两端页面，以便确认新增入口没有改变预约、资金和权限规则。
64. 作为产品负责人，我希望观察新入口的使用与预约确认情况，以便用实际结果决定后续是否投入连续场次或活动。

## Implementation Decisions

### 1. 范围、术语和交付依赖

- 本次要求是产出需求；不包含开始实现。业务增量分 P5 与 P6，P6 依赖 P5 的查询、落地页和验收完成。
- P4 的开发者工具交互和真机缺口必须继续显式记录，不能把增加功能当作已完成上线验收；真实试点仍需完成原有门禁。
- “预约”继续对应一个“具体场次”；“找搭子”继续是本人已确认预约绑定动态上的轻量招募；“会员”继续是场馆独立储值身份。
- 常约、收藏和再次预约只提供便利，不形成长期预约合同或自动续费。
- 本文将讨论中的可选实现收口为保守默认：不使用实时定位、不自动替换日期、不自动保留空位、不自动向顾客群发消息、不收取找搭子费用。

### 2. 模块边界和兼容

- 复用现有场馆/排期、预约、顾客、报表、动态/找搭子和消息服务。后台、小程序继续使用同一业务后端。
- 保持现有依赖方向 server → biz → base：持久化模型与 Mapper 在 base，规则与 Request/VO 在 biz，协议与认证在 server。
- 扩展现有查询接口时，新增筛选可选，旧调用不传新参数仍可使用。更丰富的矩阵或分页检索可增加独立查询，避免重定义旧响应含义。
- 保留现有支付组成、快照、取消截止、核销窗口、Redis 业务锁和数据库最终一致性规则。新入口最终调用同一预约创建服务。
- 不新增 SDK、通用搜索引擎、独立推荐服务或消息中间件；批量查询沿用 Mapper SQL，不在逐场馆或逐顾客循环中查库。

### 3. 时段检索与区域价格

- 用户选择日期和可用起止时间。匹配规则为：具体场次开始不早于所选起点，结束不晚于所选终点；只返回满足运动、场馆上架、场地启用、开放窗口和最晚预约规则的可订具体场次。
- 时间范围按业务时区 `Asia/Shanghai` 解释；起点小于终点。本轮不支持跨日时间范围，也不把多个相邻具体场次合并成一次两小时预约。
- 价格筛选针对单个具体场次总价，以整数分比较。场馆结果起价仅从匹配条件内的具体场次计算；无匹配具体场次不能显示全天起价冒充可订价格。
- 有时段条件时，仅展示存在匹配具体场次的场馆；无时段条件的原首页保持原行为。结果按匹配具体场次开始时间、场馆与场地标识稳定排序。
- 查询必须支持分页或有界结果，每页返回必要展示信息；不一次返回全城全部场次。进入详情后保留运动、日期、时段及价格条件，用户可以主动清除。
- 区县取场馆维护的可选结构化字段；不从详细地址自动猜测，不请求用户实时位置。既有场馆数据缺失时展示未设置；不选区县时照常可见，指定区县时只匹配明确归属。
- 场馆资料编辑复用现有资料权限。区县只是郑州内筛选，本轮不建设多城市行政区平台或地图搜索。
- 列表可用性只是查询时事实；创建预约时在服务端重新验证并发库存与当前价格，失败明确告知并允许刷新。

### 4. 常约、收藏与再次预约

- 收藏需要有效用户会话，按用户与场馆唯一保存；重复收藏/取消收藏幂等。提供本人收藏列表，账号注销时取消相关偏好记录。
- 最近预约过的场馆从本人已有已确认及终态预约中去重获取，排除仅待支付记录；不得把“曾预约”标为“已到场”。
- 再次预约只从本人预约提取场馆、运动、场地及开始时间偏好；用户明确选择新日期。旧价格、余额冻结、支付组成、服务费率、联系人快照和核销码都不直接复制。
- 用户资料中的常用联系人沿用现有确认流程。匹配偏好不可用时展示可选具体场次，由用户主动选择，不在后台自动创建替代预约。
- 停用馆、禁用场地和过期运动类型不能绕过当前预约校验；收藏不代表当前可预约，历史预约仍可按原权限查看。

### 5. 场次比较与预约服务

- 场馆详情新增按时间与场地比较的视图，保留已有按场地列表；两种展示使用同一状态和价格事实，不出现双套库存。
- 只开放单个具体场次选择。矩阵保留具体场次原始起止，不拆出可单独购买的小时格；不同长度的具体场次不能被视觉暗示为可自由拼接。
- 公开展示可订、暂时占位、已预约和不开放等状态，不公开占用者身份、联系人、预约标识、员工备注、资金或核销凭证。不可订详情限于公开原因。
- 选场/确认处前置展示取消截止、当前价格和入场须知；预约确认后服务页面按预约快照和现有状态显示。
- 已有导航和核销凭证复用；消息落地不接受客户端用户归属，必须服务端校验本人会话。
- 手机端处理横向场地较多的情况，控件有可读文字、可点击区域和加载/空/失败反馈，不仅依赖颜色。

### 6. 找搭子发现与水平

- 在现有动态入口增加“找搭子”视图；不新增第六个主导航，也不建立与当前招募重复的独立活动模型。
- 可申请列表只包含正常公开动态、有效本人已确认预约、招募中且仍有名额、未到预约开始时间的记录，并继续应用拉黑、协议和内容限权规则。
- 日期、运动和场馆筛选以绑定预约事实为准，不能由动态自由文本冒充。剩余名额按现有招募容量与通过人数定义计算，不将申请中人数误作通过人数。
- 水平首版将新招募收口为按运动配置的有限选项，默认提供新手友好、休闲和进阶三个通用标签；不是竞技评分，不自动匹配或强制验证球技。
- 历史水平文本保留为“其他水平说明”，不自动推断标签；不选择水平筛选时仍可查看，精确筛选时只匹配已选择标签的招募。
- 招募卡片显示绑定场馆、运动、时间、水平、人数及免费/预计 AA；“已订场”仅指关联预约有效，不保证申请通过或活动实际到场。
- 满员/关闭/预约取消/过期内容可以在历史或分享落地页展示状态，不能在可参加列表继续允许申请。服务器执行申请时再次验证容量和状态。
- 不修改当前发起人审核、退出、移除、取消传播、内容版本与治理规则。UGC 关闭时前端隐藏且后端拒绝对应公开读写。

### 7. 开售与空位提醒

- 新建用户提醒登记，包含本人、场馆、运动、具体日期、可用起止时间和提醒类型。首版不做全城无限条件订阅；时间匹配沿用时段检索规则。
- 可登记场馆当前预约窗口内日期，以及下一次将开放的一个日期；不开放任意远期订阅。登记列表展示预计可售规则，数据变化时仍以查询和创建时校验为准。
- 开售提醒针对匹配日期/时段进入可预约规则；空位提醒针对原不可订具体场次因取消、支付失败/超时、重新开放等原因变得可订。首次登记遇到已可订场次直接引导查看，不伪造新释放事件。
- 同一用户、相同提醒条件的重复登记幂等；用户可撤回。登记保持有效至用户撤回或该日期全部目标时段不再允许预约，同一开放事件只提醒一次。
- 同一具体场次再次被占用后再次释放，可以形成新的开放事件；不能因周期扫描一直看到可订就不断生成消息。
- 消息记录以提醒登记和可售事件稳定标识去重，数据库唯一约束作为幂等保障。生成前检查登记仍有效、场馆仍可售；业务事务回滚不得产生虚假空位消息。
- 调度可复用现有定时任务机制，基于已提交状态批量检查并生成消息。投递不持有预约/余额业务锁，不延长预约创建或取消事务。
- 首版交付站内消息和可替换 Mock 投递，显示提醒类型、匹配条件及“未保留名额”。投递失败可使用同一消息业务标识重试，成功不重复投递，不重新创建消息。
- 点击消息打开保留条件的检索或场馆页，重新查当前供给；场次已被订走时展示状态与用户可选替代。提醒不创建支付占位，不自动付款，不赋予优先预约权。
- 撤回后不再发起新投递；已经生成或外部受理的消息保留历史，打开时重新校验。账号注销后停止新消息与投递，数据保留沿用现有隐私边界。

### 8. 分时段经营分析

- 在已有经营报表增加星期 × 小时热力图、场地对比和低利用时段清单，支持现有日期范围与场馆权限，日期区间继续不超过 90 天。
- “预约利用率”以被预订分钟/可售分钟计算；一小时内仅部分被预订则按真实分钟计入，跨小时按重叠分钟分配，不按预约笔数代替时长。
- 分母为统计时段内符合公开供给规则的场地时间，包含正常开放、支付占位及已预约具体场次的可售时间基底，排除运营关闭/停用/不可供给时段；分子只计实际已确认及已履约/未到场/线下履约未跟踪预约占用，不将支付占位算成确认预约。
- 没有可售分钟显示不可售，不显示 0%；有可售分钟但未被预订显示 0%。多个运动共用一个场地时不重复计容量，同一场地同一时段仍只能被独占一次。
- 针对人工编辑具体场次与预约快照不一致的既有边界，已确认占用使用预约时间快照，并与未占用可售时段形成去重时间区间；不得使分子大于分母或改写历史预约。
- 历史分析使用留存具体场次与预约快照，不用今天的周场次或价格重算过去。既有具体场次可能已人工编辑，首版明确标注“基于当前留存供给与预约快照”，不声称还原不存在的历史开售/封场记录；不足以还原的时段显示数据不足，不填造分母。未来排期展示与历史利用率分开，不新增完整供给事件账本。
- 热力图按 `Asia/Shanghai` 自然日和小时分桶；取消统计沿用原报表预约日期口径，显示取消笔数与其统计范围，不把取消后的当前库存误作过去履约事实。
- 新分析附计算口径、查询生成时间与范围。首版复用当前数据库查询，不新增夜间数仓；查询完成时间不等于未来已发生事实。
- 金额继续分开显示线上预约经营金额、线下登记经营金额、充值实付流入、余额消费与真实收款；不把线下登记称作实收或实际到场。
- 下钻复用已有场次/预约视图权限；报表查看不自动获得顾客查看或导出权限。平台最多看场馆级汇总，不新增个人会员访问权。

### 9. 顾客分组与回访

- 在现有场馆顾客档案增加场馆内标签、最近有效预约、线上核销时间、有效预约次数及常约时段等经营信息；同一用户在其他馆的资料和余额不合并。
- 预约次数统计排除待支付和已取消，线上核销事实只来自 `COMPLETED` 预约；线下 `ENDED_UNTRACKED` 不推断已到场，展示信息明确标注来源。
- 首版提供一个清晰预设分组：曾有已完成线上预约、最近完成时间已满 30 天、且当前没有未来已确认预约的本场馆顾客。名称为“30 天未再预约”，不宣称已流失或推断其线下行为。
- 常约时段按有效预约开始小时聚合展示，次数并列时稳定排序；无有效记录时显示暂无，不构建推荐算法。
- 标签由场馆内授权人员维护，顾客与标签关系保持场馆归属校验；标签不生成会员等级，不参与计价或金额权限。
- 回访待办只针对已有场馆顾客，由授权人员创建，展示来源分组、创建人与时间、处理状态及简短备注；同一顾客同一目的不重复存在未完成待办。
- 处理状态收口为待处理、已完成、无需处理；操作留存人员和时间。备注不进入公开页，不新增用户敏感属性采集。
- 复用 `CUSTOMER_VIEW` 控制读取，在固定权限目录增加一个“顾客经营编辑”权限控制标签和回访写入；场馆超级管理员天然拥有，普通员工显式授权，撤权下一请求生效。
- 首版只生成后台可操作的回访待办，不批量导出联系方式、不自动发营销消息、不实现短信/微信群发或完整 CRM。平台仅保留场馆级汇总。

### 10. 到场提醒与投递

- 站内到场提醒以每笔已确认线上预约开始前 2 小时为默认触发点，固定规则不新增通用配置中心；确认时距开始不足 2 小时则立即补发一次，已开始或非已确认状态不补发。
- 每笔预约到场提醒以预约业务标识唯一生成，调度重复、即时补发与重试共同使用同一幂等键；生成和投递前重新检查当前状态。
- 已取消、已完成、未到场或失效预约停止新投递；历史消息不删除，点击显示当前状态。线下预约没有可信小程序用户时不发送，不按联系人手机号猜测身份。
- 消息包含预约日期时间、场馆和详情入口，不附公开核销码或敏感联系人。核销凭证只能在本人详情中按原规则读取。
- 分别记录站内消息、投递尝试与结果；Mock 成功明确为 Mock，不称为微信送达。暂时失败用原标识重试，持久失败可追踪，不阻塞取消/退款/余额事务。
- 不额外扩大外部通知渠道；真实微信订阅消息授权、模板和送达由独立接入任务承担。

### 11. 数据与接口契约

- 最小数据增量包括：用户与场馆收藏关系；可选场馆区县；招募水平标签与历史文本兼容；用户提醒登记及可售事件去重记录；场馆标签与顾客关联；回访待办与处理记录。复用现有消息、投递和预约事实，不新增平行资金账本。
- 唯一约束覆盖收藏、相同有效提醒条件、消息事件标识、顾客标签关联及同一目的的未完成回访待办。迁移追加新版本，不能重写已应用迁移或重置现有数据。
- 小程序查询接口扩展日期/时间范围/区县/价格条件，返回匹配具体场次价格与分页信息；详情矩阵返回公开状态且不包含预约者信息。
- 本人接口提供收藏与提醒登记的查询/创建/撤回；再次预约查询必须验证历史预约属于本人。用户 ID 来自服务端会话。
- 找搭子查询增加招募视图和日期/水平/剩余名额筛选，继续沿用现有申请写入口及权限规则。
- 报表接口增加分时段可售/预订分钟、利用率、场地对比与统计范围；顾客经营接口提供分组、标签与回访，并从可信身份推导场馆。
- API 返回不直接暴露持久化对象；保留统一响应与已有错误语义，新增字段提供清楚中文说明。接口契约应与运行时文档和双端请求共同验收。
- 首版仅使用现有业务事实记录完成结果，并为新增入口记录最少的入口类型与成功关联，支持判断时段找场/再订/提醒是否形成预约；不建设通用埋点 SDK 或分析平台。

## Testing Decisions

### 测试入口

以现有 HTTP API 为主业务验收入口，使用隔离 MySQL/Redis 和可控时间、Mock 外部投递建立真实数据验证查询、写入、权限和状态结果。关键页面补行为与交互验收；库存、资金、并发和定时触发规则继续在现有 Service 边界补最小回归。复用原有测试入口，不增加 Repository 或新的测试专用业务抽象。

测试只断言用户可观察结果、返回字段、权限拒绝、预约/余额事实、消息去重和统计数值，不以私有方法调用次数、组件内部排列或复制实现公式作为主要验收。

已向用户确认上述测试边界；若没有补充要求，本文按此默认口径产出，不能标为用户单独确认了测试方案。

### 已有先例

- `BookingServiceImplTest`、`PaymentServiceImplTest`、`MemberFundsServiceImplTest` 和 `RedisLockServiceTest` 提供预约、资金、回滚、幂等与锁的业务测试先例。
- `ReportServiceImplTest` 提供业务时区、90 天日期边界、独立金额口径与字段权限测试先例。
- `VenueCustomerServiceImplTest`、`SessionServiceImplTest`、`PermissionServiceImplTest` 提供顾客归属、会话、实时权限的测试先例。
- 已有 P1/P2/P3/P4 运行态脚本通过真实 HTTP 处理预约、权限、资金和社区；应复用这类验收方式，而非仅扩展 Mock 单元断言。
- 小程序已有预约/会员、员工和社区页面行为测试，以及原生模板编译；后台已有类型检查和构建。矩阵可读性、条件保留和实际点击需开发者工具/浏览器交互验证。

### 验收矩阵

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| A1 | 两家馆存在不同时间、价格与状态的具体场次；按 19:00—21:00 检索 | 仅完整落入范围且当前可订的具体场次返回；价格来自匹配场次，不暗示保证连续两小时 |
| A2 | 起止相同/逆序/跨日、非法价格、缺失区县、窗口外或临近截止 | 非法条件被明确拒绝；旧数据不猜区县；窗口与截止规则保持一致 |
| A3 | 收藏重复操作、切换账号、已停用场馆 | 收藏幂等且隔离；停用馆不允许创建预约 |
| A4 | 再次预约遇到价格变化、偏好场次满场、另一用户历史预约 | 展示现价与替代选择，不自动付款；他人历史预约拒绝读取 |
| A5 | 矩阵内开放、占位、已预约、关闭、不同长度具体场次 | 状态解释正确，只能选一个完整具体场次，无他人隐私和自由拼接错觉 |
| A6 | 找搭子审核中/隐藏/满员/到开始时间/预约取消/双方拉黑/UGC 关闭 | 可参加列表和申请行为同时受限，失效分享页不泄露成员 |
| A7 | 两用户竞争最后一个具体场次或最后一个找搭子名额 | 服务端最多成功一个，失败者不会残留冻结资金或通过关系 |
| A8 | 登记开售提醒，日期进入窗口；重复运行调度 | 同一开放事件只生成一条消息，且不创建预约/支付占位 |
| A9 | 取消/支付超时释放后再次被预订，再次释放；期间撤回登记 | 每次真实开放按事件去重，撤回后不新投递；事务回滚不生成虚假消息 |
| A10 | 打开空位提醒时该具体场次已被其他用户订走 | 明确显示当前不可订并允许用户选择替代，不承诺名额 |
| A11 | 混合长短场次、跨小时、共用多运动场地、封场、取消、人工改时 | 分钟口径可人工核对、不重复容量、分子不大于分母，不可售与 0% 区分 |
| A12 | 30 天边界、未来确认预约、仅线下未跟踪记录、其他馆数据 | 回访分组严格按已完成线上事实，当前馆隔离，不推断线下到场 |
| A13 | 标签/待办重复写入、越馆访问、员工撤权、平台请求个人资料 | 写入幂等与留痕；越权拒绝且撤权下一请求生效 |
| A14 | 开始前 2 小时调度、临近确认补发、同时触发、预约取消 | 一笔预约最多一条到场消息，失效状态不新投递，详情依然本人访问 |
| A15 | Mock 投递失败、重试、服务重启、用户注销 | 同一标识重试可追踪、不虚报微信送达、不重复消息，不影响预约与余额 |
| A16 | 时段查询/再订/提醒落地的完整预约、取消、原构成退款 | 沿用既有快照、支付占位、资金业务号和退款恢复，无新增收费规则 |
| A17 | 历史数据升级与空库迁移 | 既有资料、余额、预约、消息保留；可选字段兼容，唯一约束有效 |
| A18 | 手机、后台多视口、键盘/辅助阅读、网络失败 | 条件保留、加载重试、空结果、文字状态、可操作控件正确 |

P5 至少完成 A1-A7、A16-A18 中相关部分；P6 完成 A8-A15 并回归全部 P5 行为。完成时运行仓库规定的后端打包与相关测试、后台类型检查/构建、小程序行为检查/原生编译，运行态使用隔离测试数据，不向现有演示资金写验收流水。

## Out of Scope

- 连续多个具体场次、自由时长、跨日时段查询、线上改期、异价改期、转让与长期自动预约合同。
- 找搭子候补、自动递补、信用分、爽约处罚、平台代收 AA、最低人数成行收费及失败退款。
- 场馆组织的通用付费活动、教练、课程、课包、次卡、期限卡、会员折扣、优惠券和自动动态定价。
- 关注、私信、群聊、推荐算法、热榜、二手交易、复杂赛事和 AI 球技识别。
- 实时定位与距离排序、用户精确位置公开、多城市行政区平台和地图检索。
- 自动营销群发、短信接入、完整 CRM、对外批量导出联系方式、完整 POS/会计与新综合导出中心。
- 门禁/灯控、第三方渠道库存同步、独立原生 App、数据仓库和通用埋点平台。
- 真实微信登录/支付/退款/订阅消息、生产媒体存储/内容检测、生产部署和公开 UGC 运营。
- 改变已有场馆余额隔离、平台个人会员资料权限、线下只登记不跟踪履约、支付组成和资金状态机。

- 根产品需求继续描述 P0-P4 已有基线；本 PRD 是已同意方向的 P5/P6 增量范围。后续具体接口、迁移与执行任务以本 PRD 拆分，不回写历史未实现声明。
- 对新增选择提供明确默认规则是为便于审阅与执行；这些是本 PRD 的实现收口，不是声称已完成真实商户访谈或竞品规则验证。
- 区分场次空位提醒与找搭子候补、有效招募与实际到场、曾预约与已核销、登记经营金额与真实收款。不得把新增检索功能带来的曝光或申请直接计为实际成行。
- 成功指标先记录基线：时段检索到预约确认、再次预约入口到确认、空位提醒到重新预约、可参加列表到申请/通过、非高峰预约利用率、回访待办与后续预约。未发生核销的参与关系不能计为到场。
- P5/P6 稳定后依据使用数据择一评估连续场次、场馆固定约球活动或培训经营；它们需要独立规则设计与 PRD，不因本次方向同意而提前实现。
- 本文发布为一项产品需求并标记 `ready-for-agent`；该标签表示可据文档拆分实施任务，不代表代码已完成、测试已通过或允许直接上线。
