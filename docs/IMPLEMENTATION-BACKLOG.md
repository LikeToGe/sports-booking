# MVP 实施任务清单

## 1. 使用方式

本清单是 `PLAN.md` 的可执行分解，范围以 `PLAN.md` 和 `MVP-REQUIREMENTS.md` 为准。任务按依赖顺序执行；一个纵向切片必须完成数据迁移、服务端权限与状态约束、对应终端流程及自动化验证，才能开始依赖它的任务。

状态含义：`DONE` 已完成代码与自动化验证；`VERIFY` 已完成代码，待本地 MySQL/端到端验证；`TODO` 尚未开始；`BLOCKED` 依赖外部决策或条件。

## 2. 当前里程碑

目标：仅交付 `dev`、`test` 使用的 Mock 功能闭环，不接真实支付、不允许真实收费或公开试点。

```text
身份与租户 -> 场馆供给 -> 组合库存 -> 排期发布 -> 预约与 Mock 支付
     -> 取消退款 -> 员工核销与自动完成 -> 服务费账单 -> 全链路验收
```

## 4. 每项任务的固定实施顺序

后续新增能力仍按以下顺序实施，避免接口、数据库和页面各自演进：

1. 在数据模型、状态机和 OpenAPI 中冻结新增字段、权限与错误结果。
2. 新建 Flyway 迁移，并先补数据库约束、唯一键和索引。
3. 实现服务端事务、授权范围、审计与幂等规则。
4. 编写覆盖正常、权限拒绝、重复提交和关键并发/异常边界的测试。
5. 实现 PC 或小程序对应流程，并以真实接口联调。
6. 更新本清单状态、接口契约与验收记录。

## 5. 当前验收入口

- 后端单测与打包：在 `backend/` 执行 `./mvn-project -Dmaven.repo.local=target/m2 test` 与 `./mvn-project -Dmaven.repo.local=target/m2 package`。
- 运行态全链路：在 `backend/` 执行 `zsh scripts/verify-t06-runtime.zsh`。脚本使用本地 MySQL、临时账号和独立端口，结束后自动停止应用。
- 管理端：`admin-web/`；用户端与员工核销端：`miniapp/`。两端均直接使用统一响应信封和 `docs/openapi.yaml` 契约。
- 下一阶段仅可进入真实支付、真实退款、生产发布和试点准备，必须单独冻结需求、合规和运维方案。

## 6. 明确不进入此清单的能力

- 真实微信支付、真实退款、分账、渠道账单和生产对账。
- 场馆资料审核、自由连选、部分退款、售后、完整线下订单、财务角色和发票。
- 生产部署、公开试点和合规上线门槛。

这些能力只能在 Mock 功能闭环验收完成后，以新的里程碑拆分，不得插入当前任务队列。
